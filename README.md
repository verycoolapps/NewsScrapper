## 🔭 Vision & Mission

NEWS OMNIVERSE is a **global-scale information collection and intelligence infrastructure** — not an ordinary RSS reader. It discovers, collects, processes, organizes, and analyzes multilingual news from thousands of legitimate sources into an **evidence-aware, searchable, visual intelligence platform**.

**Mission:** Build the world's most comprehensive, intelligent, scalable, multilingual, and continuously evolving global news aggregation and intelligence platform.

> **Reality constraint:** The skill never claims to scrape every news website or every article on Earth. The internet has no complete public source directory, and access restrictions differ by publisher. The platform instead builds an **expanding source ecosystem with measurable coverage, transparent limitations, and continuous source discovery**.

**Core promise:**

```
ONE PLATFORM. EVERY REGION. EVERY LANGUAGE. EVERY IMPORTANT DEVELOPMENT.
ONE INTELLIGENT NEWS EXPERIENCE.
```

## 📊 The Processing Pipeline

```
DISCOVERY → COLLECTION → EXTRACTION → VALIDATION → NORMALIZATION
→ LANGUAGE DETECTION → TRANSLATION → CLASSIFICATION → ENTITY EXTRACTION
→ DUPLICATE DETECTION → EVENT LINKING → INDEXING → STORAGE → USER DELIVERY
```

### Extraction targets

Every article is enriched with: **title · original headline · summary · publisher · author · publication date · last updated · original URL · canonical URL · main content (only when licensed/permitted) · featured image · language · country · region · topic · keywords · named entities · referenced organizations · people · locations.**

> **Sacred data rule:** Never fabricate missing metadata — represent unavailable fields as `null`. Always preserve the original source and URL.

## 🕷️ Worldwide Crawling Engine

### Worker pipeline — every worker implements all 10 steps

```
1. Source identification   2. Permission verification   3. Request scheduling
4. Rate limiting            5. Content retrieval         6. Article extraction
7. Metadata normalization   8. Duplicate detection       9. Storage
10. Error reporting
```

### Crawl priorities & resilience

| Priority | Use case |
|----------|----------|
| 🔴 **HIGH** | Breaking news, rapidly changing events |
| 🟡 **MEDIUM** | Frequently updated sources |
| 🟢 **LOW** | Static or infrequently updated publications |

- **Adaptive crawling** — never re-request unchanged content (`ETag`, `If-Modified-Since`, `Last-Modified` conditional requests).
- **Resilience stack** — exponential backoff · retry limits · per-domain concurrency limits · request budgets · circuit breakers · dead-letter queues.
- **Isolation invariant:** one failing publisher must never interrupt the collection infrastructure.

## 🧬 Duplicate Detection — Six Levels

| Level | Method |
|-------|--------|
| **1** | Exact URL matching |
| **2** | Canonical URL matching |
| **3** | Normalized headline matching |
| **4** | Content fingerprinting |
| **5** | Semantic similarity |
| **6** | Underlying event identification |

> **Critical distinction:** *same event ≠ same article.* Independent publisher articles stay separate. Event relationships are created **without destroying source-level records**. Original publication timestamps are always preserved.

## 🧾 Evidence-Aware Intelligence

No simplistic universal "truth score" for publishers — evidence is evaluated **at the article level**.

**Displayed provenance:** original publisher · publication timestamp · supporting sources · conflicting reporting · primary-source references · attribution quality · verification status · missing information.

### Verification labels

| Label | Meaning |
|-------|---------|
| ✅ `CONFIRMED BY PRIMARY SOURCE` | Verified against a primary source |
| 🔗 `CORROBORATED BY INDEPENDENT SOURCES` | Multiple independent outlets agree |
| 📰 `REPORTED BY ONE SOURCE` | Single-source reporting only |
| ⚖️ `CONFLICTING REPORTS` | Sources disagree |
| ❓ `UNVERIFIED CLAIM` | Not yet verified |
| 🔥 `DEVELOPING STORY` | Still unfolding |

> **AI must never transform an unverified claim into an established fact.**

## 🎯 Execution Directive

> **DO NOT generate a beautiful prototype. BUILD A FUNCTIONAL PRODUCT.**

**Start by:** inspecting the existing project → defining system architecture → creating the database schema → implementing the source registry → building the first ingestion pipeline → connecting the frontend to real backend data → implementing the first functional news dashboard → testing the complete ingestion-to-display workflow.

- If the project already exists: **preserve working functionality, improve intelligently, never rewrite wholesale.**
- If credentials or external services are required: **create clear configuration instructions. Never fabricate successful integrations.** If a capability cannot be implemented, **document its exact blocker and continue**.

**Deliverables:** complete source code · frontend · backend · database schema · crawling infrastructure · AI processing pipeline · API documentation · admin dashboard · testing suite · deployment configuration · environment example · technical documentation · operational runbook.

**Final principle:** NEWS OMNIVERSE must become a **trustworthy window into the world** — not merely another news aggregator, but a continuously expanding, multilingual, evidence-aware, global information intelligence engine.

## 🔭 Visi & Misi

NEWS OMNIVERSE adalah **infrastruktur pengumpulan dan intelijen informasi berskala global** — bukan sekadar pembaca RSS biasa. Ia menemukan, mengumpulkan, memproses, mengorganisasi, dan menganalisis berita multibahasa dari ribuan sumber yang sah menjadi **platform intelijen yang sadar bukti, dapat dicari, dan visual**.

**Misi:** Membangun platform agregasi dan intelijen berita global yang paling komprehensif, cerdas, skalabel, multibahasa, dan terus berkembang di dunia.

Platform ini justru membangun **ekosistem sumber yang terus meluas dengan cakupan terukur, keterbatasan yang transparan, dan penemuan sumber berkelanjutan**.

**Janji inti:**

## 🕷️ Mesin Perayapan Sedunia

### Pipeline worker — setiap worker menjalankan 10 langkah

```
1. Identifikasi sumber   2. Verifikasi izin        3. Penjadwalan permintaan
4. Pembatasan laju        5. Pengambilan konten     6. Ekstraksi artikel
7. Normalisasi metadata   8. Deteksi duplikat        9. Penyimpanan
10. Pelaporan error
```

### Prioritas & ketahanan perayapan

| Prioritas | Kasus penggunaan |
|-----------|------------------|
| 🔴 **TINGGI** | Berita terkini, peristiwa yang berubah cepat |
| 🟡 **SEDANG** | Sumber yang sering diperbarui |
| 🟢 **RENDAH** | Publikasi statis atau jarang diperbarui |

- **Perayapan adaptif** — jangan pernah meminta ulang konten yang tidak berubah (permintaan kondisional `ETag`, `If-Modified-Since`, `Last-Modified`).
- **Tumpukan ketahanan** — exponential backoff · batas retry · batas konkurensi per-domain · anggaran permintaan · circuit breaker · dead-letter queue.
- **Invarian isolasi:** satu penerbit yang gagal tidak boleh menghentikan infrastruktur pengumpulan.

## 🚫 Standar Desain Anti-AI-Slop

### KETAT DILARANG

> ❌ Template dasbor generik · ❌ Kartu berulang tanpa tujuan · ❌ Indikator real-time palsu · ❌ Jumlah artikel palsu · ❌ Statistik penerbit palsu · ❌ Klaim cakupan global palsu · ❌ Berita placeholder yang disajikan sebagai nyata · ❌ Sitasi fabrikasi · ❌ Tombol tidak berfungsi · ❌ Grafik dekoratif dengan data fabrikasi · ❌ Tata letak tidak konsisten · ❌ Animasi tidak perlu · ❌ Navigasi kelebihan beban · ❌ Lencana verifikasi AI palsu

> **Setiap elemen interaktif harus berfungsi. Setiap titik data harus punya asal-usul yang dapat dilacak. Setiap item berita harus mempertahankan sumbernya. Setiap fitur harus menyelesaikan masalah pengguna yang nyata.**
>
> Produk terasa hidup karena data dan alur kerjanya benar-benar operasional — bukan karena efek visual.
